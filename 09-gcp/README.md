# Module 2.9 — Google Cloud Platform (GCP)

## Exercise
Architect cloud asset storage with access controls: design a storage bucket layout and define IAM role bindings to distinguish public assets from private, authenticated files.

## Bucket layout design
gs://journeybuddy-demo-bucket/
├── public/
│   ├── logo.png
│   ├── banner.jpg
│   └── terms-of-service.pdf
└── private/
    ├── user-uploads/
    │   └── <user-id>/profile-photo.jpg
    └── internal-reports/
        └── monthly-summary.pdf

**Why this layout:** separating assets by access level directly in the folder structure makes it simple to apply different permissions to each "folder", rather than having to manage access file-by-file.

## IAM role bindings

| Principal | Role | Applies to | Purpose |
|---|---|---|---|
| `allUsers` | Storage Object Viewer | `public/*` | Anyone on the internet can view/download these files — no login needed. Used for assets meant to be publicly accessible (logos, marketing images, public docs). |
| `allAuthenticatedUsers` | Storage Object Viewer | *(not used here, but available)* | Would allow any logged-in Google account to view — a middle ground between fully public and fully restricted. |
| Specific service account (e.g. `backend-service@project.iam.gserviceaccount.com`) | Storage Object Admin | `private/*` | Only the backend server (not end users directly) can read/write private files — enforces that private assets are only ever accessed through your application's authentication layer, never directly. |
| Project Owner/Editor (you, the developer) | Storage Admin | entire bucket | Full control for management purposes during development. |

## How this would be enforced in practice
1. The `public/` prefix has `allUsers` granted **Storage Object Viewer** —files here get a public URL that works for anyone, no authentication required.
2. The `private/` prefix has **no public grants at all** — by default,nothing in a GCP bucket is public unless explicitly granted. Access is only possible via:
   - A signed URL generated by the backend (temporary, expiring link), or
   - A request authenticated as a service account/user with explicit IAM permissions on that path
3. This mirrors the same pattern as Module 2.4 (Firebase Auth) — the backend verifies who the user is, then decides whether to generate a signed URL granting temporary access to a specific private file.
